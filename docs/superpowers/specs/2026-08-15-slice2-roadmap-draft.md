# Slice 2 roadmap draft — 2026-08-15 (audit synthesis)

Synthesized from three audits run at `deb810a7a` on `worktree-game-dev`: (A) upstream divergence sweep `v2.5.4..upstream-spd/master`, (B) modding-surface inventory, (C) test-coverage gap analysis. All refs below come from the source audits; verify each spec against upstream before implementing (three of six deferred-cluster specs were wrong on 2026-08-10/11).

---

## Executive summary

- **We are 1,049 commits behind upstream** (v3.0.0 through v3.3.8: 340+230+121+243+115 commits across four majors), and CPDU's tree contains none of it — no Cleric, no `heroes/spells` package, no trinkets. Several v3.x ports (B2/B3 trinkets, the Slice-2-mining bugfix bundle) **depend on Slice-1 content landing first**. The Cleric (A1) is the single best fit for the build-craft ARPG spine and must be planned as its own epic with its v3.0.1–v3.3.7 fix-tail folded in from the start.
- **The mod platform is asset/layout-complete but mechanics-poor:** art, audio, localization, dungeon topology, spawn pools, custom fixed maps, hero kits, and template-mob definitions are fully data-driven, but items (333 classes), buffs (83), traps (33), plants (14), the Generator economy, and talents are code-only. The highest-leverage unlock is a `CustomItem` interpreter mirroring `CustomMob` plus a shared JSON effects vocabulary — together they open most remaining content categories without Java.
- **~90% of `core/` — everything ported from upstream — has zero test coverage.** Of 13 test files, 8 are Keybearer-shaped; the only upstream-engine guards are `TerrainIdTest` and one Generator alignment sweep. The #1 risk (full save/load file pipeline) already conceals a live bug: `Dungeon.java:639` reads `initialVersion = bundle.getInt( VERSION )` while `INIT_VER` is written at `Dungeon.java:532` and never read back — a suspected faithful-port break that silently rewrites `initialVersion` on every load.
- **Two small test foundations (F4 HeadlessRun, F5 StubSprite+TurnPump) unlock the three highest-risk areas** (save pipeline, levelgen determinism, mob AI) and should land *before* the heavy porting waves, so ports arrive onto pinned behavior rather than un-asserted behavior.
- **Cross-cutting hazards to carry into every Slice-2 spec:** buff icons are `Pair<Asset,Asset>` not `int BuffIndicator`; sprites/tiles/music route through pack config (29–30 packs); no `Dungeon.branch` — the levelName layout graph instead; `depth/5` region math needs clamping; new terrain IDs are serialized state guarded by `TerrainIdTest`; class renames need `Bundle.addAlias` (upstream's `f06943c3e` shows the pattern); unordered-collection RNG determinism on any spawn-table change; and every new gate must be **provably able to fail** before it is trusted.

## Mod-platform gaps (prioritized, with design sketches)

Context: mods are `MODS/` folders with `mod_info.json` (`ModManager.kt`, `ModInfo.kt`); first enabled mod wins per asset path (`ModManager.getModdedAssetFilePath`, ModManager.kt:52-58); marketplace endpoint hardcoded at ModManager.kt:44, 30 packs mirrored under `marketplace/`. Every asset routes through `Asset.path` (`assets/Asset.kt`, the 1,121-line `GeneralAsset.kt`); tilesets compile at runtime from per-tile PNGs (`TileMapCompilationManager.kt`); JSON configs merge across mods (`JsonConfigRetriever.kt`); localization prepends mod bundles (`Messages.java:97-112`); JSON references Java classes by simple name via reflection (`Bestiary.kt:43-48`, `Dungeon.java:332`, `CustomLevel.java:259-379`, `RegularLevel.java:312-537`, `Mob.java:958-984`, `HeroClass.java:160-262`). Mods can *re-compose* existing Java content but can only *define* new content where a JSON interpreter exists — today, exactly one: `CustomMob`.

**Cross-cutting requirement for every hook below:** no JSON surface is schema-validated today — `pack-smoke` is structural only (manifest parse + declared-asset existence, per `PackLoaderProbe.java` javadoc; runtime boot deferred to Slice 7), and a malformed `mobs/*.json` surfaces as a runtime `SerializationException`. Every hook lands with (a) a pack-smoke schema check **provably failing** on a broken pack, and (b) save-compat by-name bundling following the `CustomMob.restoreFromBundle` pattern (CustomMob.kt:187-194).

1. **`CustomItem` — the missing mirror of `CustomMob`.** Items are the biggest class count (333, `items/**`) and there is no interpreter (grep for `CustomItem` → nothing). Sketch: `items/<name>.json` with a `kind` discriminator (`melee`, `thrown`, `potion`, `scroll`, `food`, `trinket`), per-kind stat block (tier/damage/delay/energy), sprite path + size, and an `effects` list (gap #3). One interpreter per superclass family (or one `CustomItem` with delegates), bundled by name like CustomMob.kt:187-194. Accept `custom:<name>` tokens everywhere `type` strings parse today (`ItemSpawn`, `ExtraItemSpawn`, `ItemDescription`, mob loot). Names/descriptions via pack `messages.properties`.

2. **Generator/loot-economy injection.** `dungeon.json` already externalizes PoS/SoU/styli distributions (`DungeonLayout.kt:19-21`). Extend with a `generator` block: per-`Category` prob overrides plus append entries `{type|custom, prob}` folded into `defaultProbs` before `Generator.fullReset()` (Dungeon.java:250). Turns `Generator.java:258+`'s static block into a base, not a ceiling — the prerequisite for custom items actually *dropping*. (`Generator.java:190-309` is the static class-list/prob-array surface.)

3. **Shared JSON effect vocabulary (buff/blob/damage primitives).** The pattern exists twice already: `CustomMobEnchantment` reflects into existing `Enchantment` classes with `{type, chance, strength}` (CustomMob.kt:98-119), and champion buffs apply via `Buff.affect` + reflection (CustomLevel.java:300). Generalize into an `effects` array usable by custom mobs (`on_attack`/`on_hit`/`on_death`) and custom items (`on_use`/`on_throw`): `[{apply_buff: "Burning", duration: 5, chance: 0.3}, {damage_aoe: ...}, {spawn_mob: "custom:wisp"}]` — an interpreter over the 83 existing buff classes by name. This single vocabulary is what makes #1, #7, and richer mobs expressive.

4. **CustomMob ability hooks.** Today `ranged: true` is a normal damage roll at distance with a missile sprite (`CustomMob.kt:164-167`, `CustomMobSprite.kt:52-78`); parsed `zap_frames` never drive a real cast. Add an optional `zap` block `{damage_min/max, cooldown, accuracy, effects: [...]}` (reusing #3) and behavior flags (`flee_below_hp_percent`, `summon: {type, count, cooldown}`, `on_death_spawn`). Closes most of the gap to mid-tier native mobs (Shaman/Warlock-style debuff bolts) without opening AI internals. (`Bestiary.kt:51-80` still hardcodes alt-swap pairs and the 2.5% rare chance.)

5. **Parametric generated-level recipes.** `LevelType` is binary: `regular` (named Java generator) or `custom` (fixed map) (`LevelType.kt`, `Dungeon.java:330-335`). Add `"generated"`: `{region/tileset, size_scale, room_weights: {"special.SentryRoom": 0, ...}, trap_pool: [...], trap_density, grass/water params, music}` feeding `RegularLevel`'s existing knobs — the Sewer/Prison/etc. subclasses differ mostly in exactly these parameters, and the bestiary side is already externalized. The single biggest step toward the 200-floor goal being pack-authorable.

6. **De-hardcode the region switch (1–5).** `CustomLevel.java:92-166` switches on an int for leaf colors/tiles/water, and `depth/5` math caps regions at 5. Sketch: let `region` also accept `{tiles: [per-tile paths] | tileset_name, water: path, leaf_colors: [c1, c2]}` — `TileMapCompiler` already builds sheets from arbitrary per-tile path lists at runtime, so a mod-defined sixth+ biome is mostly plumbing. Keep the int form for save/back compat.

7. **Data-driven traps and plants.** `TrapSpawn`/`PlantSpawn` are name-only references to 33/14 Java classes, yet most traps are "tinted shape + effect at cell" and plants are "effect on trample" — near-perfect fits for the #3 vocabulary: `traps/<name>.json` `{color, shape, visible_by_default, effects}`, `plants/<name>.json` `{sprite, effects}`.

8. **Shop stock lists.** `LevelScheme` already has `shop` and `price_multiplier`; stock lives in `levels/rooms/special/ShopRoom.java`. Add optional `shop_stock: [ItemSpawn-like entries + {category: "POTION", rolls: 3}]` defaulting to current behavior when absent. Small schema; immediately lets total-conversion packs (e.g. `marketplace/Exotic Dungeon`, which already rebuilds `dungeon.json` wholesale) control their economy.

9. **Hero definition beyond the kit.** `heroes/*.json` stops at inventory (`HeroConfig.kt`, `ItemDescription.kt`; consumed at `HeroClass.java:96-262`). Incremental extension: starting HP/STR, and **talent selection from the existing enum** — `{talents: {t1: ["HEARTY_MEAL", ...], t2: [...]}}` replacing the hardcoded per-class lists in `Talent.java:788+` (`initClassTalents` at :780-931; the enum carries 47 T1–T4 icon entries from :86+). Adding Keybearer required edits to `HeroClass.java` (:124), `Talent.java`, and assets; this hook lets packs re-compose classes from shipped parts (full custom classes stay code, correctly).

10. **Weighted multi-drop loot tables for custom mobs.** `CustomMobScheme.loot` is one `ExtraItemSpawn` + `lootChance` (CustomMobScheme.kt:20-21). Extend to `loot: [{spawn, chance, weight}]`. Trivial schema change; `Mob.java:958-984` already contains the interpretation logic to reuse.
